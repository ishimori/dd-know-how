# DD設計書操作

DD（Design Document）設計書を操作するスキルです。

---

## ⚠️ 重要ルール（CRITICAL）

### アーカイブ時の必須確認

**移動前に必ず実行:**
```bash
ls {DDフォルダ}/ | grep DD-{番号}
```

**フォルダが存在すれば、本体（.md）と一緒に移動すること。**

| 移動元 | 移動先 |
|--------|--------|
| `{DDフォルダ}/DD-{番号}_*.md` | `{アーカイブ}/` |
| `{DDフォルダ}/DD-{番号}/` | `{アーカイブ}/DD-{番号}/` |

**チェックリスト（必須）:**
- [ ] ヘッダ表を更新した（ステータス=`完了` または `見送り`〔固定語彙〕・補足列に成果/理由を1行・更新日を当日に）
- [ ] 仕様書同期・知見昇格に該当があれば反映した（仕様書: `doc/spec-sync-check.md` の手順／横断で効くgotcha → `doc/engineering-patterns.md`／長寿命の決定 → `doc/decisions.md`。該当なしならスキップしてよい）
- [ ] DD本体（.md）と DD番号フォルダ（存在する場合）を移動し、元の場所にDD関連ファイルが残っていない
- [ ] `bash scripts/dd-index-gen.sh` を実行してDD-INDEX.mdを再生成

**チェックリスト未確認でのアーカイブ完了報告は禁止。**

## 自然言語での呼び出し例

- 「DD-027を見せて」「27番のDD」 → DD参照
- 「DD-027を進めて」「DD-027の続きをやって」 → 再開（新規作成しない）
- 「新しいDDを作って」「〇〇のDDを作成」 → 新規作成
- 「DD一覧」「進行中のDD」 → 一覧表示
- 「DD-027をアーカイブ」 → アーカイブ
- 「DD-080の添付ファイルを作って」「関連資料を追加」 → 添付ファイル作成
- 「DDを検索」「〇〇に関連するDD」「〇〇って以前やった？」 → 検索
- 「インデックス再構築」「DD-INDEXを更新」 → インデックス再構築
- 「DDヘルスチェック」「DD運用を分析」「放置されてるDDある？」 → ヘルスチェック
- 「DD-027をCodexにレビューさせて」 → レビュー依頼（ユーザー指示時のみ）
- 「DDスキルを更新して」「dd-know-how から最新を取り込んで」 → 更新（差分レポートを見て1ファイルずつ）

## DD番号の解釈（柔軟に）

以下はすべて同じDD-001を指す：
- `DD-001` / `DD 001` / `DD001` / `001` / `1`

識別子付き（複数人・並行セッション運用時）：
- `DDI-001`（石森）、`DDSA-001`（斉藤）、`DDK-001`（kintone系列）など

## 操作手順

### 参照

1. `{DDフォルダ}/DD-INDEX.md` が存在すればINDEXからDD番号→ファイル名を解決。存在しなければ `{DDフォルダ}/DD-{番号}_*.md` をファイルスキャンで検索（なければアーカイブも検索）
2. **DD本体のみ読み込む**（リンク先は自動で読み込まない）
3. DD番号フォルダ（`DD-{番号}/`）があれば通知
4. 「何をしますか？」と確認

### 再開（既存DDの続き）

番号付きの依頼は既存DDの作業として扱い、新規作成しない（guides.md・テンプレートは読まない）。

1. DD本体を読み、未完了のタスクとログの最後を確認する。`git status --short` で他のセッションの変更が混ざっていないかも見る
2. ステータスで分ける: `完了`・`見送り` → 終わっている旨を伝える／`保留` → 補足の再開条件を満たしているか確かめる／`確認待ち` → 何を待っているかを伝える（残りが人手の動作確認だけなら、閉じることを提案する — guides.md §3）
3. 作業を始めたらステータスを `進行中` にし（更新日も）、未完了のタスクから進める

### 新規作成

1. **`doc/templates/guides.md` を Read** → アプローチと使用するテンプレートを決定
2. **`doc/templates/dd_template.md`（+ 差分テンプレート）を Read** → DD骨格を取得
3. `{DDフォルダ}/DD-INDEX.md` が存在すればINDEXから最大番号を取得。存在しなければファイルスキャン（`ls`）で取得。識別子付き系列（`DDK-` 等）で作る場合は**その系列内の最大番号**から連番を取る
4. 次の連番でファイル作成: `DD-{連番}_{タイトル}.md`
5. テンプレートの `{番号}` `{タイトル}` `{日付}` を置換し、アプローチとリスク判定（guides.md §10）を冒頭に1行ずつ記載して作成。ステータスは初期値「検討中」のまま — 固定語彙6種（guides.md §3）以外を書かない
6. **出力するDDにテンプレートのHTMLコメント（`<!-- ... -->`）を残さないこと**
7. **Playwright MCP 確認**（画面を伴う実装Phaseがある場合のみ）: Playwright MCP が利用可能か確認する。利用不可の場合、DDログに「Playwright MCP 未導入: エビデンスは手動キャプチャで代替」と記載する
8. **DD-INDEX.md 更新**: `bash scripts/dd-index-gen.sh` を実行してインデックスを再生成する。スクリプトが存在しない場合はユーザーに通知し、手動でのインデックス更新を提案する
9. **セルフチェック**: `bash scripts/dd-health.sh --dd DD-{番号} --new` を実行し、⚠️があれば修正してから完了報告する（スクリプト未導入ならスキップ）

> **⛔ テンプレート必須ルール**: 上記ステップ1・2 の Read に失敗した場合は**エラーとして停止**し、ユーザーにパスを確認すること。自力でDD構造を生成してはならない。

### 一覧

1. `{DDフォルダ}/DD-INDEX.md` を Read して内容を表示
2. DD-INDEX.md が存在しない場合は `bash scripts/dd-index-gen.sh` を実行して生成。スクリプトも存在しない場合はファイルスキャンで一覧を表示

### 検索

キーワードでDDを横断検索する。

1. **Phase 1: インデックス検索（高速）**
   - `{DDフォルダ}/DD-INDEX.md` を Read し、テーブル行からキーワードにマッチするDDを抽出
   - Phase 1 で見つかれば結果表示 →「全文検索もしますか？」と確認
   - Phase 1 で 0件なら自動的に Phase 2 へ

2. **Phase 2: 全文検索（必要に応じて）**
   - Grep で `{DDフォルダ}/` と `{アーカイブ}/` の `.md` ファイルを検索
   - 10件超はタイトルマッチを優先表示

### インデックス再構築

`bash scripts/dd-index-gen.sh` を実行して DD-INDEX.md を全量再生成する。スクリプトが存在しない場合はユーザーに dd-know-how の `templates/scripts/dd-index-gen.sh` のコピーを提案する。

### ヘルスチェック（運用分析）

DD運用が期待通り回っているか（クローズ漏れ・滞留・ログ形骸化・表記ゆれ）を機械検証する。

1. `bash scripts/dd-health.sh` を実行してレポートを取得（単一DDは `--dd DD-{番号}`）
2. レポートをそのまま貼らず、「要対応」の各DDに推奨アクション（アーカイブ / 再開・見送りの判断 / ログ補完）を添えて提示する。判断に迷う項目は該当DDを開いて根拠を確認してから提案する。確認待ちで止まっているDDは、残りが人手の動作確認だけなら、完了にして確認していない範囲をログへ残すことを提案する（guides.md §3）
3. スクリプトが存在しない場合は dd-know-how の `templates/scripts/dd-health.sh` のコピーを提案する

### レビュー依頼（ユーザー指示時のみ — 自動実行しない）

レビューはDDタスクに組み込まれていない。ユーザーが「DD-{番号}を（Codexに）レビューさせて」と指示した時のみ実施する（運用の考え方: guides.md §10）:

1. **依頼書生成**: `{DDフォルダ}/DD-{番号}/codex-review-request.md` を作成。差分だけでなく背景情報（DD目的・スコープ・対象差分・設計意図・制約）を含め、仕様一致・権限・バリデーション・回帰・テスト不足の観点を指示する。実装前の計画（DD）のレビューなら、依頼書は `codex-review-plan-request.md`、結果は `codex-review-plan-result.md` とし、差分には起票のコミットを `--commit` で渡す（guides.md §10）
2. **実行**: `bash scripts/codex-review.sh --request <依頼書> --out {DDフォルダ}/DD-{番号}/codex-review-result.md [--uncommitted|--base <br>|--commit <sha>]`（所要数分になりうるためバックグラウンド実行推奨。スクリプト未導入なら結果を得る手段がない旨をユーザーに伝える）
3. **結果反映**: findings への対応（採用/見送りと理由）をDDログに記録する。実行生ログは削除し、残すのは request / result の2ファイルのみ

### 更新（dd-know-how からの取り込み）

配布物は一括では取り込まない。差分を見て、取り込むファイルをユーザーと1つずつ決める。安定して動いているなら、理由（セキュリティ修正・このリポジトリで起きているバグ・欲しい機能）がない限り更新しない。

1. `bash scripts/dd-update.sh` で差分レポートを出す（ファイルは変更されない）
2. レポートを要約してユーザーに提示し、**取り込むファイルを1つずつ確認する**
   - 上流だけ変更／未導入: レポートに表示される `cp` で取り込む
   - 両方変更: このリポジトリの改変を残したまま、レポートの「反映すべき上流の変更」だけを手で反映する
   - ローカルだけ変更: 取り込むものはない（上流でも役立つ修正なら dd-know-how への還元を提案する）
3. `git diff` をユーザーに見せ、**コミットはユーザーの確認後**（stage は対象ファイルを明示）。`dd-index-gen.sh` を取り込んだら `bash scripts/dd-index-gen.sh` で DD-INDEX を再生成する
4. スクリプトが存在しない場合も `bash ../dd-know-how/tools/dd-update-core.sh --target .` で同じレポートを出せる（dd-know-how が別の場所ならそのパス）。初回導入なら dd-know-how の `doc/UPGRADE-NOTICE.md` 最新版の手順を提案する

### ログ追記

1. 対象DDの「ログ」セクションに日時とメモを追記
2. フォーマット: `### {日付}` の下に `- {メモ内容}`

### アーカイブ

→ **「⚠️ 重要ルール」セクションの手順に従うこと**

## 注意事項

- タスク完了時は `[x]` に変更
- ステータス変更は固定語彙6種（検討中/進行中/確認待ち/保留/見送り/完了。guides.md §3）から選ぶ。説明・成果はヘッダ表の補足列（1行）へ書き、更新日もあわせて更新する
- DD完了時は完了報告（DD番号・変更ファイル・受け入れ基準の結果・リスク判定・残課題）を出す。レビューはその報告を見た人間が必要に応じて別モデルへ指示する
