# 実践ガイド — 61リポジトリのDD運用から

DDを使っている61のリポジトリで、2025年12月ごろから2026年10月までに4,500件を超えるDDが書かれました。このガイドは、それらを読み比べて分かったことをまとめたものです。

- 別々のリポジトリが、互いに知らないまま同じ形に行き着いた使い方
- 多くのリポジトリで繰り返されたつまずきと、その対策

ルールの正本は [templates/guides.md](../templates/guides.md) です。ここでは、そのルールがなぜそうなっているかを実例で示します。事例は匿名化し、文面は言い換えています。数字は調査時点（2026年10月）の集計です。

## 1. 何に使われているか

DDは機能開発の記録だけに使われているわけではありません。タイトルのキーワードで分類すると、次のとおりです（機械的な分類なので目安です）。

| 種類 | 割合 | 例 |
|------|-----:|----|
| 機能の追加・改善 | 58% | 画面・API・帳票の追加（ほかの種類に当てはまらないものを含む） |
| 調査・検証 | 12% | 既存システムの解析、受領した資料の読み解き、精度・性能の評価 |
| リファクタ・整理 | 7% | 使われていないコードの除去、不要なテーブルの削除 |
| 設計・方針 | 6% | 複数案の比較と決定（実装は後続のDDで） |
| バグ修正 | 6% | 実行時エラーの真因の特定 |
| 運用・インフラ | 5% | 依存ライブラリの脆弱性対応、バックアップの構築 |
| 資料・移行・テスト・性能 | 6% | 提案書や打合せ資料、サービス終了に伴う切り替え、E2Eの整備 |

コードを1行も書かないリポジトリもあります。セキュリティ調査、受領した資料のナレッジ化と要件の抽出、提案書づくりなどで、どれも同じテンプレートで回っています（読み替え方は §3.3）。

コミットの8〜9割にDD番号が付いているリポジトリが多く、`git log --grep DD-042` を打てば、そのDDに関わるコミットがすべて出てきます。

## 2. DDを作るか・作らないか

DDを作るかどうかの基準を、少なくとも6つのリポジトリが、毎セッション読まれる指示ファイルに書いていました。キットの3項目をそのまま写したものもあれば、独自に広げたものもあります。広げた中身はほぼ共通でした。

| DDを作る（いずれか） | DDを作らない |
|------|------|
| 仕様・業務ルール・データ構造・API・認可・AIプロンプトを変える | 原因が明確な単純バグの修正 |
| 判断の理由を後から説明する必要がある（選択肢を比べた・方針を決めた） | 誤字・リンクの修正 |
| 途中でユーザーの確認を挟む | 振る舞いを変えないリファクタ・明白な依存更新 |
| 調査・検証・資料作成で、結論と根拠を残したい | 仕様に影響しない見た目だけの変更 |
| | 既存DDのタスク消化 |

あわせて決められていたのが次の2つです。

- **DDを作らない変更も、何をなぜ変えたかをコミットメッセージに残す**
- **作らないつもりで始めても、影響が広いと分かった時点でDDを起こす**

反対向きの事例もあります。DDが要る作業を起票の前に進めてしまい、ユーザーが止めて起票し直したケースです。「いきなりコードを書かない」は今も効いています。

> キットへの反映: [templates/guides.md](../templates/guides.md) §1「DDを作るか」と、AGENTS.md の雛形の「DD省略可」の1行。

## 3. 現場で定着した使い方

### 3.1 親子DD — 大きな作業は分ける

枝番の子DD（`DD-050-1` など）は、48のリポジトリで2,300件を超えます。分ける単位は「ユーザーの確認1回」です（guides.md §6）。

親DDに子DDの連鎖の計画表を置き、起票時の想定が外れたら訂正を書く、という使い方がありました。レビューを受けて子DDを足したときも、そのことを親に書いています。

一方で、子DDだけが進み、親のタスクはすべて未チェックのまま残った例もあります。索引の上では、親の状態が読めなくなっていました。親を地図として使うなら、子を閉じるたびに更新します（guides.md §6「親DDは地図にする」）。

### 3.2 DD番号のフォルダ — 証拠と資料の置き場

DD番号のフォルダ（`DD-050/`。guides.md の「添付フォルダ」）は、51のリポジトリで2,300個を超えます。中身はスクリーンショットが大半で、検証記録とシナリオがそれに続きます。ほかに次のようなものが置かれていました。

- 別モデルのレビューの依頼書と結果
- 次のセッションへの引き継ぎメモ
- 画面のモック（合意した版は合意の証拠として凍結し、以後の修正は別の場所で行う）
- 打合せ資料や、先方への確認依頼の下書き

DD本体は200行以内に保ち、長くなるものはこのフォルダへ移します。アーカイブのときはフォルダごと移します（`/dd archive` のチェックリストに入っています）。

フォルダは git に入ります。受領したデータの原本や認証情報は置かず、別の置き場を決めておきます。原本を上書きしないこと、コミットする文書に個人名を書かないことを規約にしたリポジトリもあります。

### 3.3 コードを書かないDD — 調査・資料作成・運用

調査や資料作成も、同じテンプレートで書けます。項目は次のように読み替えます（guides.md §11）。

| 項目 | 読み替え |
|------|---------|
| 受け入れ基準 | 答える問いと、答えが出たと言える条件 |
| 🔬 機械検証 | 根拠を確かめ直せる手段（出典・再現できるコマンド・件数の突き合わせなど） |
| Phase | 調べる範囲の区切り。最初に打ち切り条件を書く |

実例は次のとおりです。

- **資料からの抽出**: 受領したPDFをテキストにして、機能の一覧表を作るDD。抽出した文書の項目を grep で数え、元資料に載っている機能の数と一覧表の件数が合うかを確かめました
- **インフラの構築**: クラウドに保管先を作り、本番で有効にするDD。コードは書いていません。機械検証は権限シミュレーターの出力で、許可したい操作だけが通り、ほかは拒否されることを確かめました
- **打合せの準備**: 配布用の1枚、社内の進行表、判断が要る点に印を付けた想定問答を作るDD。資料の数字を元データと照合するスクリプトを添付に置き、禁止語（個人名など）が残っていないことの grep を完了条件にしました
- **原因の調査**: 調べた結果、バグではないと分かったDD。その根拠を書いて閉じました。「問題は無かった」も結論です

**確度を書き分ける。** 資料の解析が中心のリポジトリでは、結論ごとに出どころのラベルを付けていました（［資料で確認］［先方の説明］［ユーザーの方針］［推測］［未確認］）。前のセッションやLLMの推測が、いつの間にか確定事項として扱われるのを防ぐためです。

**打ち切り条件を先に書く。** 精度を評価するDDでは、チェックポイントごとの撤退基準を起票時に書いていました（例: 構築で2時間を超えたら手順を切り替える、合計6時間を超えたら途中成果を記録して撤退する）。実際には2.5時間で結論が出ています。基準が無いと、評価は「もう少しで良くなりそう」のまま続きがちです。

### 3.4 見送りで閉じる

やらないと決めたDDは「見送り」で閉じます。アーカイブ済みの見送りは148件ありました。理由と、再検討する条件を補足列とログに残します。

- **ユーザーレビューで受け入れられなかったデモの親DD**: 原因を4点に整理して製品の方向を変え、「保留のまま残すより終える」と判断して見送りにしました。検証済みのコードは消さず、実装を終えた子DDは完了のままアーカイブしています
- **評価で全体の精度が下がった機能**: 既定をオフにして閉じました
- **方針の転換で優先度が下がったDD**: 転換を決めたDDを番号で示して、見送りにしました

保留のまま残ったDDは、時間がたつほど再開するかどうかの判断が難しくなります。見送りで閉じておけば、少なくとも「なぜやらなかったか」は検索で見つかります。

### 3.5 完了と残りを分ける

閉じられずに残るDDで多いのは、「ほとんど終わっているが、一部だけ待っている」状態です。

**人手の確認だけでクローズを止めない。** あるリポジトリでは、実装・検証・レビュー対応まで終わったDD2件が、正味15分の実機確認を待って6週間閉じられず、後続のDDまで止まりました。一方、全件の自動回帰は約4分で終わります。待ち時間が機械検証より2桁長い状況で人手の確認をクローズ条件にしても、リスクは下がらず、滞留が増えるだけです。そのリポジトリは次のように決め、キットも同じルールを取り入れました（guides.md §3）。

- 残りが人手の確認だけなら、ほかの受け入れ基準を満たした時点で完了にする
- 確認していない範囲（何を確かめていないか・問題が出たら何が起きるか）をログに1行残す
- 問題が出たら、そのとき別のDDを起こす
- 確認そのものが目的のDD（リリースや移行の判定）は例外とし、確認してから閉じる

**止まった部分だけを切り出す。** 9種類のテンプレートを移すDDで、2種類だけが外部からの原本の提供待ちになったリポジトリがあります。その2種類を子DD（保留。補足に再開条件）に切り出し、親は7種類で完了にしました。別のリポジトリは、未確認の事項を「扱い・担当」の表にして閉じ、続きを後続のDDへ渡しています。

逆向きの失敗もありました。確認のPhaseが未チェックのまま、何も書かずに完了にした例です。未確認のまま閉じるなら、何を確認していないかを必ず書きます。

### 3.6 セッションの引き継ぎと並行作業

**引き継ぎ。** セッションをまたぐ作業では、次のセッションが最初に読むものを書いておきます。

- いちばん軽いのは、DDのログの最後に「次にやること」を書く方法
- 大きな作業では、DD番号のフォルダに引き継ぎメモを置く。中身は、読む順番のDD一覧、決まったこと、まだ決まっていないこと
- コンテキストの残りが3割になった時点で、引き継ぎ専用のDDを起こした例もある。次のセッションは、そのDDの「次のアクション」から始めた

引き継ぎメモの中でも、DDは番号で指します。パスやリンクで書いたメモは、アーカイブの後に読み返すと指す先が無くなっていました（guides.md §4）。

**並行作業。** 複数のセッションが同じリポジトリで動くと、DD番号の衝突と、互いの作業の巻き込みが起きます。

- 系列ごとに識別子を付ける（`DD-001` と `DDK-001`）。詳しくは [customization/parallel-sessions.md](customization/parallel-sessions.md)
- `git add -A` を使わず、stage するファイルを明示する（他のセッションの作業や認証情報を巻き込んだ事故がきっかけ）
- 共有の作業ツリーでは、stage する前にそのファイルの差分を読む
- 実装中の変更はこまめにコミットする。別のセッションが作業ツリー全体を戻す操作をして、未コミットの変更が消えた事故があったため。作業ツリーを書き換える git の操作は、`git -C <パス>` で対象を明示する

### 3.7 別モデルの意見を記録する

別モデルのレビュー（README「別モデル・クロスレビュー」）は、記録の残し方まで含めて定着していました。

- **依頼書と結果はDD番号のフォルダに残し、指摘ごとの採用・見送りと理由をログへ。** 指摘9件のうち4件を直し、5件は今回の範囲外として見送った、と1件ずつ表にしたDDがあります。後から「なぜ直さなかったのか」と聞かれても答えられます
- **計画のレビュー。** 実装の前に、DD（計画）を別モデルにレビューさせたリポジトリがあります。計画の段階で3件、実装の段階でさらに3件の指摘が出ました。計画の指摘は、着手前に直せています。取り消せない操作（本番の設定切り替えなど）の前にも効きます（guides.md §10）
- **レビューが収束しないとき。** 3回目のレビューでも新しい指摘が10件出たDDでは、ユーザーの判断で実装役とレビュー役のモデルを入れ替えました。その後のレビューでは、新しい指摘は0件、次に1件でした
- **チャット型のLLMに相談したとき**も、相談文・回答・要約をDD番号のフォルダに残していました。誰に何を聞いてどう判断したかが、コードと同じ場所に残ります

### 3.8 結論を「今の姿」の文書へ移す

DDは変更の記録（フロー）なので、時間がたつほどアーカイブに沈みます。「今どうなっているか」を知りたい人が毎回DDを全部読まずに済むよう、結論は現在形の文書（ストック）へ移します。キットでは、アーカイブ時のチェックリストで仕様書・engineering-patterns.md・decisions.md への反映を確認します（README「ドキュメント体系: フローとストック」）。

コードの少ないリポジトリでも、同じ形が育っていました。

- 既存システムの置き換えを調べるリポジトリでは、調査結果を蒸留した参照ファイル集を置き、「経緯はDDに、今この瞬間に正しい事実だけをここに」と決めていました。AIが毎回DDの全文を読まずに済むようにするためです
- 知見を昇格するかは「半年後の別の作業でも効くか」で判定し、昇格しなかったものも理由を残していました（engineering-patterns.md の冒頭にある基準）

### 3.9 運用そのものを測る

DDの運用が重くなっていないかを、DDを使って測ったリポジトリがあります。

- コミット147本のうち75本（51%）が、ドキュメントとDD運用だけの変更だった
- ドキュメントの執筆量はコードの2.3倍あり、その65%は終わったDDの本文と添付の証拠だった。書いた後は、ほとんど読まれていない
- この結果を受けて、記録を git に寄せ、レビューを1回にまとめ、完了処理を1コミットにした

別のリポジトリは、運用を軽くする変更の前に判定基準を決めておき、対象のDDが終わるたびに実測表へ1行を足しました。「良好」と判定してから、キットへの反映を提案しています。キットの軽量化（v7 の自動レビューの廃止など）も、こうした利用先での計測がきっかけです。

## 4. よくあるつまずきと対策

| つまずき | 調査で見えたこと | 対策 |
|------|------|------|
| 閉じ忘れ | 完了なのに未アーカイブのDDが80件。アーカイブ済みなのに進行中・確認待ちなどのままのDDが100件超 | `/dd health` のクローズ漏れ検出。アーカイブはチェックリスト（ステータスの更新を含む）に沿って行う |
| 確認待ちの放置 | 数か月前から確認待ちのままのDDが、複数のリポジトリにある | §3.5。`/dd health` は14日を超えた確認待ちを警告する |
| 案件終了時の放置 | 終わった案件に、進行中のDDが残る | 終えるときに `/dd list` で残っているDDを全件確かめ、完了か見送りに決める。`/dd health` は期限を過ぎたものしか挙げない（guides.md §3） |
| 書きすぎ | 200行を超えるDDが4分の1を占めたリポジトリ（最長は約600行） | 本体は200行以内。詳細は添付と子DDへ（§3.9 の計測も参照） |
| 索引の読み取り失敗 | ヘッダ表の位置のずれや、HTMLコメントの残骸で、索引の行が欠ける | テンプレートの形を崩さない。作成直後に `dd-health.sh --dd DD-xxx --new` |
| リンク切れ | アーカイブの後、ほかのDDや引き継ぎメモからのリンクが切れる | 本文では他のDDを番号で指す（guides.md §4） |
| ステータスの表記揺れ | 全体で620通りの書き方（「完了」「✅完了」「Done」「完了（要確認）」など） | 固定6種＋補足列。`/dd health` を回しているリポジトリでは揺れ0件 |
| 指示ファイルと実態のずれ | 指示ファイルが、存在しないフォルダや古い命名規則を指している | AGENTS.md を正本にし、CLAUDE.md は `@AGENTS.md` の1行だけにする |
| 配布物の手コピー | キットにない部品を手でコピーし、リポジトリごとに中身がずれる | 取り込みは `dd-update.sh` の差分レポートを見て1ファイルずつ（[UPGRADE-NOTICE.md](UPGRADE-NOTICE.md)） |

## 5. 頼み方の早見表

| 頼み方 | 起きること |
|------|------|
| 「〇〇のDDを作って」 | アプローチとリスクを判定して起票する（調査や資料作成も同じ） |
| 「DD-123 の続きをやって」 | DDを読み、未完了のタスクから再開する（新規作成しない） |
| 「〇〇って以前やった？」 | 索引と全文から、関係するDDを探す |
| 「DD-123 を Codex にレビューさせて」 | 依頼書を作り、別モデルに差分を見せる。指摘の採否はログへ |
| 「放置されてるDDある？」 | ヘルスチェック。対処の提案が付く |
| 「DD-123 をアーカイブ」 | 仕様書と知見への反映を確かめてから移す |
| 「次のセッション用に引き継ぎを書いて」 | DDのログの最後か、DD番号のフォルダの引き継ぎメモに書く |
