# DD作成ガイド

## 1. DDを作るか・アプローチ選択

### DDを作るか

| DDを作る（いずれか） | DDを作らない |
|------|------|
| 仕様・業務ルール・データ構造・API・認可・AIプロンプトを変える | 原因が明確な単純バグの修正 |
| 判断の理由を後から説明する必要がある（選択肢を比べた・方針を決めた） | 誤字・リンクの修正 |
| 途中でユーザーの確認を挟む | 振る舞いを変えないリファクタ・明白な依存更新 |
| 調査・検証・資料作成で、結論と根拠を残したい | 仕様に影響しない見た目だけの変更 |
| | 既存DDのタスク消化 |

- DDを作らない変更も、何をなぜ変えたかをコミットメッセージに残す（形式は `機能名: 概要`）
- 作らないつもりで始めても、影響が広いと分かった時点でDDを起こす

### アプローチ

ユーザーが指定すればそれに従う。指定がなければ自動判断し、DD冒頭に選択理由を1行明示する。

| 優先順 | 判断基準 | アプローチ | 差分テンプレート |
|:------:|---------|-----------|----------------|
| 1 | 既知のバグ修正（再現→修正→Before/After検証） | バグ修正 | `dd_template_bugfix.md` |
| 2 | 画面の新規作成・大幅変更（見た目の合意が必要） | モック先行 | `dd_template_mock.md` |
| 3 | 画面の振る舞い中心（操作→結果の検証が必要） | E2E駆動 | `dd_template_e2e.md` |
| 4 | 計算・遷移・ビジネスロジックが中心 | TDD | `dd_template_tdd.md` |
| 5 | 上記以外 | 標準（探索的実装） | `dd_template.md` のみ |

記載例: `> アプローチ: モック先行（画面新規作成のため）`

コードを書かない作業（調査・検証・資料作成・運用作業）も「標準」を使い、§11 の読み替えに従う（記載例: `> アプローチ: 標準（調査 — コード変更なし）`）。

Phaseごとにアプローチを混在させてもよい（例: BE=TDD、FE=モック先行）。AskQuestion はスコープ自体が不明瞭な場合の最終手段。

## 2. テンプレート適用

`dd_template.md` を骨格とし、差分テンプレートがあれば該当Phaseを差し替える。

## 3. ステータスと補足列（固定語彙）

ヘッダ表は4列: `| 作成日 | 更新日 | ステータス | 補足 |`

**ステータス列は固定6種のみ。** 装飾（絵文字・太字）や説明文の同居は禁止 — KANBANビューア・DD-INDEX生成・ヘルスチェックが列の値を機械判定するため。

| ステータス | 意味 | 終端 |
|-----------|------|------|
| 検討中 | 起票〜方針決定前（新規作成時の初期値） | |
| 進行中 | 実装・作業中 | |
| 確認待ち | ユーザーレビュー・判断待ち | |
| 保留 | 意図的に中断。再開条件を補足へ | |
| 見送り | やらないと決定。理由（再検討する条件があればそれも）を補足へ | ✅ |
| 完了 | 全Phase完了 | ✅ |

- **終端（完了・見送り）になったらアーカイブする**（`/dd archive`）
- **人手の確認だけでクローズを止めない**: 確認待ちは、人の判断（仕様の合意・採否）を待つ状態。残りが実機や目視の動作確認だけなら、ほかの受け入れ基準を満たした時点で完了にし、確認していない範囲（何を確かめていないか・問題が出たら何が起きるか）をログに1行残す。問題が出たら別DDを起こす。例外は、確認そのものが目的のDD（リリース・移行の判定など）と、確認してから閉じるとユーザーが決めたもの
- **止まった部分は切り出して閉じる**: 外部の回答・資料・環境を待つ部分だけが残ったら、その部分を子DD（`保留`。補足に再開条件）へ移し、元のDDは完了にする
- **案件や作業系列を終えるとき**は、`/dd health` で終端でないDDを洗い出し、完了か見送りに決める（再開の見込みがあるものだけ `保留` にして再開条件を書く）
- **補足列**: 1行・簡潔（詳細はログへ）。完了時は成果要約（DD-INDEXの「主な成果」列に転載される）、保留・見送りは理由・再開条件、進行中はPhase進捗など（空欄可）
- **ステータス列を空にしない**（ビューアは列位置で解析するため、空セルは誤読の原因になる）。セル内に半角 `|` を書かない
- ステータス・補足を変えたら**更新日も更新**する

## 4. 命名規則

```
DD-{番号}_{タイトル}.md       # 標準（番号は3桁ゼロパディング）
DD-083-1_子タイトル.md        # 親子DD（同テーマの続き）
```

**他のDDの指し方**: 本文では `DD-083` のように番号だけで書き、パスやリンクを書かない（アーカイブで場所が変わるとリンクが切れるため。子DDの「親DD:」行も同じ）。添付は「DD-083 の verification.md」のように番号とファイル名で書く。自分の添付フォルダへの相対リンク（`DD-083/xxx.png`）は、フォルダごと移動するので使ってよい。

## 5. フォルダ構成

既定レイアウト（**実配置はプロジェクトルートの `.dd-config` が正**。スクリプト・フックはこれを参照する）:

```
doc/
├── DD/                       # DD_DIR
│   ├── DD-001_タイトル.md    # DD本体（常に直下）
│   ├── DD-001/               # 添付フォルダ（あれば）
│   └── DD-INDEX.md           # 自動生成インデックス（手動編集禁止）
└── archived/DD/              # ARCHIVE_DIR: 完了したDD（添付フォルダごと移動）
```

**❌ 禁止:** `attachment/` や `attachments/` 等の汎用的な名前のフォルダを作成しないこと。

番号管理: 新規作成時はDDフォルダとアーカイブの両方から最大番号を確認。

## 6. DD本体のサイズ管理

**200行以内。** 超えそうなら:
- **添付ファイル分離**: 50行超の仕様・エビデンス・モック・シナリオ → `DD-{番号}/` に配置
- **子DD分割**: 別テーマとして切り出せる部分 → 子DDに

### 粒度＝レビューゲートの単位

**1つのDDは、1回のレビューサイクル（作業→成果物→ユーザーレビュー→合意）で完結する単位にする。**

レビューゲートが1回 → DD単体で完結（親子にしない）:
```
DD-070: ログ出力フォーマット変更（実装→レビュー→完了）
```

レビューゲートが2回以上 → 親DD + 子DDに分割:
```
DD-050: XX機能開発（親。管理用。実装は子DDで行う）
DD-050-1: DB設計（ER図レビュー→合意）
DD-050-2: 画面モック（HTMLレビュー→合意）
DD-050-3: FE/BE実装（動作確認→合意）
```

**親DDは地図にする**: 子DDの一覧（順番・ステータス）を親に置き、子を閉じるたびに更新する。起票時の想定が外れたら、親に訂正を1行書く。最後の子が終わったら親も閉じる（親だけ更新が止まって残りやすい）。


## 7. タスク記述ルール

- 各タスクに対象ファイルパスを明記する
- 変更内容は具体的に書く（「更新」「改修」だけは禁止）
- 各Phaseの末尾に🔬機械検証タスクを入れる（実行コマンド + 期待結果）。**各Phaseの機械検証はそのPhaseで触った領域の対象テスト・lint・型検査に限定する。全回帰（`npm run check` 等の全件実行）は完了前チェックの1回だけ**（redになった修正後の再実行を除く。Phaseごとに全件を回さない）
- 受け入れ基準（DD本体のセクション）の各項目に、対応する検証タスク（機械検証・E2Eシナリオ・エビデンス）があることを確認する。対応のない基準は検証漏れ
- **同じ情報を2箇所に書かない**: 論点表で合意した内容を決定事項へ再転記せず、決定事項からは論点表を参照する（逆も同様）。ログは1判断1行で記録する（散文の経過記録をしない）
- **上記以外の進め方は実装モデルに任せる**: DDは「何を作るか・何ができたら完成か」を固定する文書であり、作業手順書ではない。Phaseの切り方・実装順・リファクタ判断・調査の深さを細かくタスク化しない

## 8. テスト戦略

テストコードを書く前に、必ず自然言語でシナリオを作成しユーザーの合意を得ること。E2E駆動の場合はPlaywright MCPによるブラウザ自動操作で検証する。詳細は差分テンプレート（`dd_template_e2e.md` / `dd_template_tdd.md` / `dd_template_mock.md`）を参照。

小規模DDでは、シナリオ合意を**起票直後の仕様確認に一本化**し、実装途中に個別のユーザー確認ゲートを追加しない（確認ゲートは起票時＋完了時の2回まで）。

## 9. エビデンス収集

**画面を伴う実装Phaseでは、Phase完了時にスクリーンショットエビデンスを取得する。**

### 対象

- 画面の新規作成・変更を含むPhase（アプローチ問わず）
- バグ修正で画面表示が変わるもの

### 手順（バグ修正の場合）

1. **コード修正前**に画面を開き、問題箇所を赤枠ハイライト → キャプチャ（Before）
2. コードを修正する
3. **コード修正後**に同じ画面を開き、修正箇所を赤枠ハイライト → キャプチャ（After）
4. `DD-{番号}/` フォルダに配置（番号部分のみ。例: `DD-061/`。タイトルは含めない）
5. DD本体に Before/After テーブルを記載

Before を撮り忘れると後から再現できない。**必ず修正前に撮ること。** バグ修正DDでは、実装Phaseの最初のタスクに「📸 Beforeキャプチャ取得」を入れること（guides.md を参照しなくてもタスクリストで気づけるようにする）。

### 手順（新規開発の場合）

1. 実装完了後、追加した箇所を赤枠ハイライト → キャプチャ
2. `DD-{番号}/` フォルダに配置（番号部分のみ。例: `DD-061/`）
3. DD本体にエビデンステーブルを記載

### 赤枠ハイライト

キャプチャ前に Playwright MCP の `browser_evaluate` でCSSを注入し、注目箇所を赤枠で囲む。人間がスクリーンショットを見た瞬間に「どこを見ればいいか」が分かるようにする。

```javascript
// 例: 単一要素
document.querySelector('.target-element').style.cssText += 'outline: 3px solid red; outline-offset: 2px;';

// 例: 複数要素を一括ハイライト
document.querySelectorAll('.target-elements').forEach(el => {
  el.style.cssText += 'outline: 3px solid red; outline-offset: 2px;';
});
```

**いつ囲むか:**
- **バグ修正**: 修正した箇所（Before: 問題箇所、After: 修正箇所）
- **新規開発**: 今回追加した列・ボタン・セクションなど、レビューで確認してほしい箇所

赤枠は「ここを見てください」というマーカー。囲む対象に迷ったら「人間がこのスクリーンショットだけ見てOK/NGを判断できるか？」を基準にする。

### ファイル命名規則

```
{コンテキスト}-{before|after}-{説明}.png
```

例:
- `bug61-before-incorrect-allowance.png`
- `bug61-after-fixed-allowance.png`
- `employee-list-after-column-added.png`

### DD本体への記載形式

```markdown
## エビデンス

| Before | After |
|--------|-------|
| ![before](DD-{番号}/xxx-before-yyy.png) | ![after](DD-{番号}/xxx-after-yyy.png) |
| 説明（❌ 問題の状態） | 説明（✅ 修正後の状態） |
```

新規作成（Beforeなし）の場合は After のみの一覧でよい。

### Playwright MCP が利用できない場合

手動でスクリーンショットを取得し、同じフォルダ・命名規則で配置する。DDログに「手動キャプチャ」と明記すること。

## 10. リスク判定とレビュー運用

### リスク判定（起票時に1行）

**認可・認証 / DBスキーマ・マイグレーション / 外部I/F / 機密情報・決済** のいずれかに触れるかを判定し、DD冒頭に1行書く。

記載例: `> リスク: あり（DBマイグレーション — Phase 2）` / `> リスク: なし`

- **あり** → 該当項目に対応する検証タスクを必ず置き、完了報告にもリスク項目を明記する（人間がレビュー要否を判断する材料になる）
- リスクありのPhaseは、着手前に設計の要点（触るファイル・I/F・データフロー）を短くユーザーに確認してよい

### レビューは人間が都度指示する（DDタスクに組み込まない）

別モデル・別視点でのレビューは、DDのタスクとして自動実行しない。運用:

1. 実装モデル（Opus / Codex のいずれか1つ）がDDを完走し、**完了報告**を出す（記載内容: `development-flow.md` Step 5）
2. 人間が完了報告のリスク・規模を見て、必要なら**もう一方のモデル**にレビューを指示する
3. 指摘への対応は実装したセッション側で行い、対応結果（採用/見送りと理由）をDDログに1行記録する

Codex CLI 導入済みプロジェクトでは、ユーザーの指示を受けた Claude が `bash scripts/codex-review.sh --request <依頼書> --out <結果ファイル>` でヘッドレスレビューを依頼できる（依頼書にはDD目的・スコープ・対象差分・設計意図を含める）。**ユーザーが指示した時のみ実行**すること。

**計画のレビュー**: 大きな親DDや、取り消せない操作（本番データの移行・削除、本番設定の切り替え）を含むDDは、実装前のDD（計画）をレビューに出してもよい。依頼書と結果は `DD-{番号}/codex-review-plan-request.md` / `codex-review-plan-result.md` とし、実装のレビュー（`codex-review-request.md` / `codex-review-result.md`）と分ける。差分には起票のコミットを渡す（`--commit <sha>`）。

## 11. コードを書かないDD（調査・資料作成・運用作業）

テンプレートはそのまま使い、次のように読み替える（アプローチは「標準」。§1）。

| 項目 | 読み替え |
|------|---------|
| 受け入れ基準 | 答える問いと、答えが出たと言える条件（例: 現行システムの帳票は何種類あり、それぞれ誰が使うか → 一覧に全帳票と利用者が載っている） |
| 🔬 機械検証 | 根拠を確かめ直せる手段。出典（ファイル・行・シート・URL）、再現できるコマンド、元資料との件数・数値の突き合わせ、禁止語（個人名など）の grep、権限シミュレーターの出力など |
| Phase | 調べる範囲の区切り。最初の Phase に打ち切り条件（使ってよい時間・撤退の基準）を書く |

- **確度を書き分ける**: 結論ごとに出どころを付ける（例: ［資料で確認］［先方の説明］［推測］［未確認］）。前のセッションやLLMの推測を、確かめずに確定事項として書き写さない
- **「問題は無かった」も結論**: 調べた結果、問題が無いと分かったら、その根拠を書いて完了にする
- **結論は現在形の文書へ移す**: アーカイブ前に、調べた結果を `doc/` の現在形の文書（調査結果のまとめ・仕様書・decisions.md など）へ移す。DDには経緯と根拠を残す
